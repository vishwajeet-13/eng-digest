## 1. GitHub moved 430,000 lines of Copilot code to a faster language, mostly with AI
*GitHub Engineering (via ByteByteGo)* · AI / Backend

**In one line:** GitHub rewrote the engine behind its Copilot products from TypeScript into Rust, and one developer finished it in a few months using AI agents.

**What happened:** The Copilot "runtime" is the shared engine that runs AI agents inside many GitHub products. It was written in TypeScript, so every app that used it had to start a second process and carry about 100 MB of extra memory. GitHub wanted a plain library any app could load directly, so it chose Rust. About 430,000 lines of production code moved over, a job that would normally need a big team and a couple of years. The work went piece by piece: each part was swapped for Rust in one pull request, behind a thin temporary bridge. Fleets of AI agents did much of the reading, porting and reviewing, and old end-to-end tests decided whether a change could merge. In one test, a client setup that took 5.25 seconds now took 292 milliseconds, and peak memory in a 10-client test fell from 1383 MB to 126 MB.

**Why it matters:** It shows what a huge AI-assisted rewrite looks like in practice: about $120K in AI costs, some subtle bugs, and strong tests as the safety net.

**New words:** **Runtime** — the engine that runs a program's core logic · **Pull request** — a proposed code change that others review before it is merged · **Regression** — something that worked before but breaks after a change

## 2. How LinkedIn's AI reviews 40,000 code changes a week
*ByteByteGo* · AI / Engineering process

<video controls playsinline preload="none" poster="https://vishwajeet-13.github.io/eng-digest-videos/2026-11-11/2.jpg" src="https://vishwajeet-13.github.io/eng-digest-videos/2026-11-11/2.mp4"></video>

**In one line:** LinkedIn built a team of AI reviewers that check each other, so humans get fewer, better comments to read.

**What happened:** When AI writes code faster, the slow step becomes reviewing it. LinkedIn first tried a vendor's ready-made reviewer, but its comments were noisy and generic, so engineers asked to opt out. A single AI model with LinkedIn's own rules made things up and sometimes pointed at the wrong line. So LinkedIn built a multi-agent system. Several AI "subagents" review the same change on their own, without seeing each other's work. An orchestrator merges duplicate findings, and a different model double-checks any finding only one agent raised. Weak or cosmetic findings are dropped before anything is posted. Today it covers over 40,000 pull requests a week, and most reviews appear before a human opens the change.

**Why it matters:** Letting AIs cross-check each other cuts hallucinations and keeps engineers' trust in the comments.

**New words:** **Hallucination** — when an AI confidently states something untrue · **Orchestrator** — the "manager" program that hands work to others and combines results · **Diff** — the lines a change adds, removes or edits

## 3. Airbnb open-sources Skipper, a workflow engine that lives inside your service
*Airbnb Engineering* · Backend

<video controls playsinline preload="none" poster="https://vishwajeet-13.github.io/eng-digest-videos/2026-11-11/3.jpg" src="https://vishwajeet-13.github.io/eng-digest-videos/2026-11-11/3.mp4"></video>

**In one line:** Skipper lets a program remember its progress, so a multi-step job can continue after a crash.

**What happened:** Some jobs take many steps, wait for a person, or call other services. If the server restarts halfway, it must know what already happened. Many tools solve this with a separate central "orchestration" service. Airbnb wanted each service to own its workflows using its own database instead. In Skipper, you write a workflow as a Java or Kotlin class. Each action's result is saved as a checkpoint. After a crash, the workflow runs again from the top, and finished actions simply return their saved results. Waiting, such as for a one-day human review, doesn't hold a thread. Skipper is now open source under the Apache 2.0 license.

**Why it matters:** Teams get crash-safe multi-step processes without running another big system. The trade-off is that they own the database load and recovery themselves.

**New words:** **Workflow** — a multi-step process written as code · **Checkpoint** — a saved record of a finished step · **Idempotent** — safe to run twice with the same result

## 4. Why AI agents that work for weeks need "durable execution"
*Martin Fowler's site (Kiran Prakash)* · AI / Architecture

**In one line:** Agents that take days or weeks must survive crashes, so their program keeps a record of each step.

**What happened:** The article follows an agent called Stock Replenisher. It gets quotes, waits two days for a manager's approval, places an order, then waits three weeks for delivery. In that time the process can restart, calls can fail, and messages can arrive late, twice, or never. Durable execution is the pattern that keeps a record of the result of every step that touches the outside world. After a failure, the program runs again, skips finished steps, and rebuilds its state from the record. The author warns that durable is not the same as correct: an agent can still make a bad decision, and the world can change while it waits.

**Why it matters:** As agents take on long jobs, crash recovery becomes basic plumbing, not a nice extra.

**New words:** **Long-horizon agent** — an AI agent working on a task over days or weeks · **Durable execution** — running code so progress survives failures · **At least once** — a step may be retried, so it may happen more than once

[Read the full post →](https://martinfowler.com/articles/durable-execution-agents.html)

## 5. AWS shows how app teams can fail over to another region by themselves
*AWS Architecture Blog* · Cloud

**In one line:** Even behind a company's central security gateways, an app team can switch its app to a backup region without asking anyone.

**What happened:** In banks and hospitals, all traffic passes through a central fleet of security proxies. That makes it hard for an app team to practise or run disaster recovery, because they depend on a busy central team. AWS shows a pattern using Amazon ARC Region Switch, a managed tool that runs a failover plan step by step. The plan can promote a database copy, scale servers, change DNS health checks and call custom code. The central team owns the network links between regions. The app team owns a private DNS record that decides which region gets traffic. Flipping that record needs no meeting. AWS says the cost is one extra network hop between regions.

**Why it matters:** Teams can prove their disaster plan works on demand, which auditors in regulated industries expect.

**New words:** **Failover** — switching to a backup system when the main one fails · **DNS** — the internet's phone book that maps names to addresses · **RTO** — recovery time objective, how fast you must be back up

## 6. Meta shares TLX, a tool for squeezing more speed out of GPUs
*Meta Engineering* · AI / Infrastructure

**In one line:** TLX adds finer control to Triton, a popular GPU programming tool, so engineers can use new chip features without writing hard low-level code.

**What happened:** AI models run on GPU "kernels", small programs for the chip. Meta writes more and more of them in Triton, which is easy to use but hides how groups of GPU workers cooperate. New NVIDIA chips like Hopper and Blackwell depend on exactly that cooperation, such as one group loading data while another computes. CUDA, the low-level option, can express it but takes lots of code. Meta calls the gap a "missing middle" and built TLX, which lets engineers spell out that teamwork inside Triton, only where needed. Meta says TLX now helps production work in recommendation training, recommendation inference and large-scale LLM pretraining.

**Why it matters:** Faster kernels mean cheaper and quicker AI training and serving.

**New words:** **GPU kernel** — a small program that runs on a graphics chip · **Warp group** — a team of GPU threads working together · **Compiler** — a tool that turns code into instructions a chip can run

[Read the full post →](https://engineering.fb.com/2026/11/10/open-source/tlx-a-hardware-native-gpu-compiler-for-production-ml/)
